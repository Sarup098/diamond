Introduction to Software Engineering

Software Engineering is the systematic, disciplined, and quantifiable approach to the development, operation, and maintenance of software. It combines software (collection of executable code, libraries, and documentation) with engineering (well-defined, scientific principles).

"A systematic collection of good program development practices and techniques — an engineering approach to develop software."

Program vs. Software

Program Small, single-user, limited functionality; poor maintainability, no documentation.
Software Large, multi-user, systematically designed, thoroughly tested, good UI & documentation, team-developed.

Evolution of SE

Software engineering evolved from Art → Craft → Engineering over 60 years:

  • Esoteric / build-and-fix era
  • Craft: unorganised use of experience
  • Engineering: systematic, scientific basis

Software Development Life Cycle (SDLC) Models

An SDLC model graphically depicts the different phases a software evolves through, accompanied by descriptions of activities in each phase. It promotes systematic, disciplined development — essential for team-based ("programming-in-the-large") projects.

Adherence to a suitable life cycle model helps produce good quality software and minimizes chances of time and cost overruns. A documented process model is a mandatory requirement of ISO 9000 and SEI CMM quality standards.

Phase Entry & Exit Criteria

A good SDLC defines entry (conditions before a phase starts) and exit criteria (conditions before a phase ends). Example: SRS phase exit = SRS document ready, internally reviewed, and customer-approved.

Classical Waterfall Weaknesses

  • No feedback paths between phases
  • Difficult to accommodate change requests
  • Inefficient error corrections
  • No overlapping of phases

Iterative Waterfall

  • Adds feedback paths within phases
  • Phase containment of errors
  • Still no incremental delivery
  • Limited customer interaction
  • No support for risk handling

Other Key SDLC Models

V-Model

Each development stage maps to a corresponding test stage. Strong on testing activity, quality test cases, efficient manpower distribution.

Prototyping Model

Quickly builds a prototype to explore requirements. Iterative development. Good when requirements are unclear. Risk: scope creep.

Incremental Model

Delivers software in increments. Each increment adds functionality. Allows early delivery and feedback.

Evolutionary Model

Evolves through iterations. Requirements may change between iterations. Combines prototyping with incremental delivery.

Spiral Model

Risk-driven iterative model. Each loop: plan → risk analysis → development → evaluation. Best for large, high-risk projects.

RAD (Rapid Application Development)

Fast development with frequent releases. Iterative + quick user feedback. Flexible to accommodate changes during development.

03

Requirements Analysis & SRS

A requirement is a capability or condition required from the system to be developed. The goal of requirements analysis is to clearly understand customer needs and organize them into an SRS (Software Requirements Specification) document.

Three Activities

Requirement Gathering Elicitation from stakeholders via study of existing docs, interviews (Delphi technique), task analysis, scenario analysis, form analysis.
Requirement Analysis Remove anomalies, inconsistencies, incompleteness. Clarify data input/output, procedures, complexities, and external interfaces.
Requirement Specification Document gathered and analyzed requirements in the SRS document.

SRS Document

A comprehensive description of the intended purpose and environment of the software. An SRS minimizes development cost and time.

Types of Requirements

  • Functional — what the system does
  • Performance — speed, accuracy, frequency, throughput
  • External Interface — hardware/software interfaces
  • Design Constraints — how (not just what)
  • Quality Attributes — reliability, portability, maintainability

Software Quality Attributes

Correctness Reliability Efficiency Integrity Usability Survivability Maintainability Portability Reusability Expandability

Good SRS reduces development cost by up to 40% (fewer change requests later). It serves as: agreement between customer & developer · basis for cost/schedule estimation · basis for validation & verification · foundation for user manual.

Users of SRS

Users & Customers Software Developers Test Engineers Documentation Writers Project Managers Maintenance Engineers

Requirements Problems

Anomaly A requirement that is unusual, incorrect, or deviates from the norm.
Inconsistency Two requirements that contradict each other.
Incompleteness Requirements that are missing information or leave scenarios undefined.
04

WRSPM Model

The WRSPM (World, Requirements, Specifications, Programs, Machines) model is a framework for understanding and structuring requirements within the SDLC.

World (W) Real-world context and assumptions — market, competitors, user demographics, domain knowledge that form the foundation for understanding requirements.
Requirements (R) User's language-based understanding of what they want from the solution (e.g., "I want to withdraw money from an ATM").
Specifications (S) System language-based description of how the system meets requirements — interface definition, steps a user must follow (insert card, enter PIN, select amount).
Programs (P) Software developers' implementation of specifications — all code and underlying frameworks.
Machines (M) Hardware specifications supporting the system — physical components like servers, cash dispensers, security mechanisms.

WRSPM provides a structured approach to managing requirements complexity, ensuring that the distinction between user requirements and system specifications is captured clearly. Most goals are met when the end user is happy and satisfied.

05

Software Design

The design phase transforms the SRS document into a design document that is implementable in a programming language. The design process identifies modules, control relationships, interfaces, data structures, and algorithms.

Classification of Design Activities

Preliminary (High-Level) Design

Identifies modules required, control relationships, and interfaces. Also called software architecture or structural design.

Detailed Design

Specifies data structures and algorithms for each individual module. Documented in module specifications.

Characteristics of Good Software Design

Correctness Design correctly realizes all requirements in the SRS document.
Understandability Consistent, meaningful names; decomposition; abstraction; modularity; layered structure.
Efficiency Makes efficient use of time and space resources.
Maintainability Easy to modify when requirements change or defects are discovered.

Modularity

A modular design decomposes a problem into a set of modules with limited interactions. It is a basic characteristic of any good design solution, enabling independent development, testing, and maintenance.

Layered Design

In a layered design, modules are arranged in a hierarchy where a module can only invoke functions of the immediately lower layer. This implements control abstraction — lower modules are unaware of higher layer modules, like workers unaware of senior management structure.

06

Function-Oriented Design & DFDs

Function-Oriented Design views a system as a black box providing services to users. High-level functions are successively decomposed (top-down decomposition). The methodology used is Structured Analysis / Structured Design (SA/SD).

Structured Analysis (SA)

Transforms SRS into a DFD model (functional decomposition). Based on principles:

  • Top-down decomposition approach
  • Divide and conquer principle
  • Graphical representation using DFDs

Structured Design (SD)

Transforms the DFD model into a structure chart (module hierarchy). Maps all identified functions into a module structure = high-level design / software architecture.

Data Flow Diagrams (DFDs)

A DFD (bubble chart) is a hierarchical graphical model showing processing activities and data interchange. Primitive symbols:

SymbolRepresentationNotes
Circle / BubbleFunction/ProcessAnnotated with function name
RectangleExternal EntityInteracts with system (input/output)
Directed Arc →Data FlowAnnotated with data name; shows flow direction
Open RectangleData StorePersistent data repository

DFD Levels

Context Diagram

Most abstract. Entire system = single bubble. Shows external entities, input data, and output data. Establishes system context.

Level 1 DFD

Contains 3–7 bubbles. Derived from high-level functional requirements in SRS. Shows major processes and data flows between them.

Decomposed DFDs

Each bubble is "exploded" (factored) into sub-functions until each bubble can be described by a simple algorithm. Also called bubble decomposition.

Object Modeling & UML

UML (Unified Modelling Language) is an OMG-standard modeling language accepted by ISO. It provides graphical notations to document design and analysis models. Based on work from Booch, Rumbaugh, and Jacobson (OMT, Booch methodology, OOSE).

Basic OO Concepts

Object Tangible real-world entity or conceptual entity that stores data and supports operations (methods). Objects provide excellent decomposition of large problems.
Class A collection of similar objects with same attributes and methods. A class is an Abstract Data Type (ADT) — data accessed only through methods, and it can be instantiated into objects.
Inheritance Derived class inherits from base class (super/parent). Enables generalization-specialization. Multiple inheritance: inheriting from more than one base class.
Association & Link Classes that can invoke each other's methods. A link is an instance of an association. Can be binary, n-ary, or unary (recursive). Links are dynamic; associations are persistent.
Composition & Aggregation Part/whole relationships. A Book is composed of Chapters. Composite objects contain other objects.
Dependency Class A depends on B if changes to B require changes to A. Arises when a method takes another class as argument or when implementing an interface.

Key OO Principles

Abstraction

Selective examination — consider only relevant aspects, suppress irrelevant details. Supported via feature abstraction (class hierarchy) and data abstraction (private data + methods).

Encapsulation

Data of an object is encapsulated within its methods. Benefits: protection from unauthorized access, data hiding, weak coupling.

Polymorphism

An object may behave differently for the same operation depending on its type. Types: Static polymorphism (compile-time) and Dynamic polymorphism (runtime).

Genericity

Parameterize class definitions. Define a generic Stack<T> and instantiate as integer stack, character stack, etc.

Use Case Model

The use case model (constructed first) captures the user's view of the system. A use case answers: "What can the different categories of users achieve using the system?" All other models must conform to the use case model.

08

Coding & Coding Standards

The coding phase begins after the design phase. Each module specified in the design document is coded and unit tested in isolation. After all modules are coded, integration and system testing is undertaken.

Coding Standards

Professional software organizations require programmers to adhere to coding standards — rules for naming variables, code layout, error return conventions, etc. Compliance is verified during code review. Non-compliant code is rejected.

Benefits of Coding Standards

  • Uniform appearance across engineers
  • Facilitates code understanding & reuse
  • Promotes good programming practices

Standard vs. Guideline

Coding Standards: Mandatory rules. Verified during code inspection. Violations cause code rejection.

Coding Guidelines: General suggestions. Left to developer discretion.

Code Review

After a module is coded, code review verifies coding standards compliance and detects errors early. Code reviews are more efficient than testing for defect elimination — finding and fixing errors is cheaper before testing begins.

09

Software Testing

"Testing is the process of executing a program with the intention of finding errors." — Glenford Myers
"Testing can show the presence of bugs but never their absence." — Edsger Dijkstra

Good Testing Practices

  • A good test case has a high probability of detecting undiscovered defects, not just showing the program works
  • It is impossible to effectively test your own program
  • Every test case must include a description of the expected result
  • Avoid non-reproducible or on-the-fly testing
  • Write test cases for both valid and invalid input conditions
  • Thoroughly inspect results of each test
  • As detected defects increase, probability of more undetected defects also increases
  • Assign your best people to testing
  • Testability should be a key objective in software design
  • Never alter the program to make testing easier

Levels of Testing

Unit Testing

Tests each module in isolation. Focuses on: algorithms & logic, data structures, interfaces, independent paths, boundary conditions, error handling.

Integration Testing

Tests combined modules. Necessary because: one module can adversely affect another; subfunctions combined may not produce desired result; interfacing errors appear; timing/resource contention issues surface.

Validation Testing

Tests against the SRS requirements. Verifies that the product does what the customer wants.

System Testing

Tests the full product against its requirements. Conducted on the complete integrated system.

Acceptance Testing

Customer validates that the delivered software meets agreed-upon requirements. Final gate before release.

Regression Testing

Re-runs tests after changes to ensure existing functionality is not broken by new code.

Alpha Testing

Performed at developer's site by end users. Controlled environment.

Beta Testing

Performed at customer's site. Real-world environment. Precedes product release.

Integration Strategies

Top-Down Integration Start from top-level modules, use stubs for lower-level ones. Tests control flow early.
Bottom-Up Integration Start from lowest-level modules, use drivers for higher ones. Tests utilities early.
Big Bang Integrate all at once. Easy to plan, hard to debug. Suitable for small systems.

Software Project Management

Software Project Management is the art and science of planning and leading software projects. Its goal: enable engineers to work efficiently towards successful completion of a project.

Common Causes of Project Failure

  • Unrealistic or unarticulated project goals
  • Inaccurate estimates of needed resources
  • Badly defined system requirements
  • Poor reporting of project status
  • Unmanaged risks
  • Poor communication (customer ↔ dev ↔ users)
  • Use of immature technology
  • Inability to handle project complexity
  • Sloppy development practices
  • Poor project management
  • Stakeholder politics
  • Commercial pressures

SE Project Management Complexities

Invisibility Changeability Complexity Uniqueness Exactness of Solution Team & Intellect-Intensive

Project Manager Responsibilities

Project Planning

  • Size, effort, cost estimation
  • Scheduling (WBS, Gantt, PERT)
  • Project staffing
  • Proposal writing

Monitoring & Control

  • Track milestone completion
  • Risk management
  • Configuration management
  • Client interaction & reports

Scheduling, CPM & PERT

Scheduling consists of deciding which tasks are taken up when and by whom. The project manager monitors timely completion and takes corrective action on schedule slippage.

Scheduling Steps

  • Identify all major activities needed to complete the project
  • Break each activity into smaller tasks
  • Determine dependency among tasks (task A depends on B if A needs B's output)
  • Represent information in an activity network
  • Establish time duration estimates for each task
  • Determine task start and end dates from the activity network
  • Determine the critical path (chain of tasks determining project duration)
  • Allocate resources to tasks (Gantt chart)

Work Breakdown Structure (WBS)

Recursively decomposes activities into smaller tasks. Tasks are the lowest-level work units — assigned to developers and scheduled. End of each important activity = a milestone.

Critical Path Method (CPM)

Minimum Time (MT) Minimum project completion time = maximum of all paths from start to finish.
Earliest Start (ES) Maximum of all paths from start to this task. ES = max(EF of all predecessors).
Earliest Finish (EF) EF = ES + duration of task.
Latest Start (LS) LS = LF − duration of task. Computed backwards from project end.
Latest Finish (LF) LF = min(LS of immediate successors). Latest time to finish without delaying the project.
Slack Time (ST) ST = LF − EF. Amount of time a task can be delayed without affecting project end. Critical path tasks have ST = 0.
// CPM Calculation Formulas
ES = max(EF of all predecessor tasks)
EF = ES + Duration
LF = min(LS of immediate successors)
LS = LF - Duration
ST = LF - EF  // Slack / Float time

// Critical Path: all paths where duration == MT
// Tasks on critical path: ST == 0

There can be more than one critical path. The critical path may change as the project progresses when tasks complete ahead or behind schedule. Tasks on the critical path require special attention from the project manager.

Risk Management

A risk is any anticipated unfavorable event that can occur while a project is underway. Risk management has three activities:

Risk Identification

Project Risks: budgetary, schedule, personnel, resource, customer-related (software invisibility).

Technical Risks: design, implementation, interface, testing, maintenance problems.

Business Risks: building excellent product no one wants; losing budgetary commitment.

Risk Assessment

For each risk, assess:

  • r = likelihood the risk becomes real
  • s = consequence/severity if it does
  • Priority p = r × s

Risk Mitigation (3 Strategies)

  • Avoid the risk — change the plan
  • Transfer the risk — outsource/insure
  • Risk Reduction — build prototype, plan containment
// Risk Priority and Leverage
Priority = r × s

Risk Leverage = (Risk Exposure Before − Risk Exposure After) / Cost of Reduction

Software Configuration Management (SCM)

Software consists of source code, design documents, SRS, test documents, and user manuals. The configuration is the state of all project deliverables at any point in time. SCM effectively tracks and controls the configuration throughout the software lifecycle.

Halstead's Software Metrics

Halstead's Software Science (Maurice Halstead, 1977) analytically measures size, development effort, and cost directly from source code. Programs are treated as sequences of tokens classified as operators or operands.

Basic Measures

η₁ (eta1) Number of distinct operators in the program.
η₂ (eta2) Number of distinct operands in the program.
N₁ Total number of operator occurrences.
N₂ Total number of operand occurrences.
// Vocabulary and Length
Vocabulary η = η₁ + η₂
Length N = N₁ + N₂

// Program Volume
Volume V = N × log₂(η)

// Difficulty and Effort
Difficulty D = (η₁/2) × (N₂/η₂)
Effort E = V × D  // mental discriminations required

// Time to implement
Time T = E / S  // S = 18 (empirical Stroud number)

// Estimated Length
N̂ = η₁ × log₂(η₁) + η₂ × log₂(η₂)

Operators for ANSI C include: arithmetic (+ - * /), logical (&& ||), comparison (== != < >), assignment (= += -=), and keywords (IF ELSE WHILE FOR RETURN etc.). Variable names in declarations are NOT operands — only variables used in expressions count.

Agile Development Model

Agile is a group of development methods based on iterative and incremental approaches where requirements and solutions evolve through collaboration between self-organizing, cross-functional teams. The Agile Manifesto was introduced in 2001 by 17 individuals (The Agile Alliance).

Individuals and interactions over processes and tools · Working software over comprehensive documentation · Customer collaboration over contract negotiation · Responding to change over following a plan.

12 Agile Principles

  • Satisfy the customer through early and continuous delivery of valuable software
  • Welcome changing requirements, even late in development
  • Deliver working software frequently (weeks to months, prefer shorter)
  • Business people and developers must work together daily
  • Build projects around motivated individuals; give them support and trust
  • Most efficient communication is face-to-face
  • Working software is the primary measure of progress
  • Agile promotes sustainable development — constant pace indefinitely
  • Continuous attention to technical excellence and good design
  • Simplicity — maximizing the amount of work not done — is essential
  • Best architectures emerge from self-organizing teams
  • Team reflects regularly on how to become more effective and adjusts

Agile Development Models

Crystal Feature-Driven Development (FDD) Scrum Extreme Programming (XP) Lean Development Unified Process

Scrum (Most Widely Used)

Scrum is a lightweight process framework for agile development. Lightweight = process overhead kept minimal to maximize productive time.

Sprint

Actual time period (typically 2 weeks; range: 1 week – 1 month) when the scrum team works to finish an increment. More complex work = shorter sprint. Scope can be re-negotiated during a sprint. All events occur within the sprint. Duration must remain consistent throughout development.

Scrum Roles

  • Product Owner — manages product backlog
  • Scrum Master — facilitates the process
  • Development Team — self-organizing, cross-functional

Scrum Events

  • Sprint Planning
  • Daily Standup
  • Sprint Review
  • Sprint Retrospective

Scrum Artifacts

  • Product Backlog
  • Sprint Backlog
  • Increment (working software)

DevOps

DevOps combines development (Dev) and operations (Ops) to increase efficiency, speed, and security of software development and delivery. It automates and streamlines the SDLC so code moves from development to production quickly, reliably, and securely.

Phases of the DevOps Lifecycle

Jira, Confluence, Trello

Build
Jenkins, Maven, Docker
Test
Selenium, JUnit, SonarQube
Release
Git tags, Jenkins
Deploy
K8s, Ansible, ArgoCD
Operate & Monitor
Prometheus, Grafana

Deployment Strategies

Blue-Green Deployment

Two identical environments. Traffic is switched between them for a seamless update with zero downtime. Rollback = switch back.

Canary Deployment

New version released to a small percentage of users first. Validates changes safely before full rollout.

Rolling Updates

Update is gradually pushed out to all users. Instances are updated one at a time. Minimal downtime.

CI/CD — Continuous Integration & Delivery

CI/CD is the backbone of modern DevOps, bridging development and operations by automating building, testing, and deployment. It transforms software release from a high-stress monthly event into a routine, non-event happening multiple times daily.

The Three Pillars

Continuous Integration (CI)

Goal: Prevent "Integration Hell."

Developers merge to main branch daily. Automated system builds code and runs unit tests on every commit. Failed tests → build rejected → developer notified immediately.

Continuous Delivery (CD)

Goal: Be ready to release at any moment.

Code is automatically deployed to staging/testing after CI passes. Integration and load tests run. Codebase always in a deployable state, but production push is a manual decision.

Continuous Deployment (CD)

Goal: Eliminate human intervention.

If all automated tests pass in staging, code is automatically deployed to production. Requires extremely robust, trustworthy automated test suites.
